# Magick Studio v1.1.0: post-release audit

| | |
| --- | --- |
| Audited release | `v1.1.0` (tag → commit `0acf0ad`, identical to `main` at audit time) |
| Audit date | 2026-11-02 |
| Audit branch | `audit/v1.1.0-post-release` |
| Scope | Shared backend, GTK (Linux) and PySide6 (Windows) interfaces, packaging, installer, CI, tests, docs |
| Method | Code review, reproductions on Fedora 44 (ImageMagick 7.1.2-34), Linux CI containers, GitHub-hosted Windows Server 2025 runners, and four independent read-only reviews (security, backend/concurrency, Windows packaging, Linux/CI). Each review finding was re-checked against the code or reproduced before being accepted. |

## Summary

v1.1.0 has **no Critical findings**. There is **one High** security finding: ImageMagick
chooses its decoder from file *content*, so a "photo" that is really PostScript, PDF, SVG
or MVG is passed to Ghostscript or a vector renderer. Ghostscript has a history of
sandbox escapes, so this is a credible attack path for files from untrusted sources.
It was confirmed by reproduction and is fixed on the audit branch. This issue already
existed in v1.0.0.

The other confirmed issues are Medium or Low. They are:

- **Resource exhaustion:** a 380 KB PNG used more than 3 GB of memory.
- **Linux interface:** quitting during a batch, non-UTF-8 file names, and responsiveness.
- **Windows installer:** gaps such as uninstalling while the app runs.
- **CI:** checks that could pass vacuously.

There was no data loss, overwrite or crash of the processing engine. Output safety
(atomic writes, collision-free names, originals untouched) held up in every test,
including concurrent runs.

**Recommendation:** keep v1.1.0 published and prepare **v1.1.1** with these fixes. No
emergency action is needed. The High issue needs a crafted file opened by the user. On
Linux, exposure also depends on Ghostscript being installed. On Windows, the bundled
ImageMagick has no Ghostscript, but its built-in SVG renderer can embed other local
images into the output. Until v1.1.1 ships, users should avoid processing images from
untrusted sources.

## Findings

Severity follows user impact and exploitability: **Critical**, **High**, **Medium** or **Low**.
Status is **Fixed** (on the audit branch, with a regression test or CI check),
**Partly fixed**, **Open** (documented, recommended for later), **Accepted** (no change
planned) or **Not reproduced**.

### Security and supply chain

#### SEC-1: Decoder chosen by file content: disguised PostScript/PDF/SVG/MVG reach Ghostscript and vector renderers. **High**. Fixed.

- **Where:** `image_processor.py`. The input was passed as a bare path to `identify`, the
  conversion command and `thumbnail()`.
- **Evidence:**
  - A PostScript file named `scan.jpg` was identified as `PS`. Processing it ran Ghostscript
    and produced a 611×791 PNG of the rendered text.
  - An SVG named `vacation.jpg`, with `<image xlink:href="/path/private.png">`, was rendered
    by ImageMagick's internal SVG renderer (MSVG). The referenced local image was embedded
    in the output (mean red 1.0, green 0).
  - ImageMagick 7.1.2 itself blocks explicit coders such as `text:` inside SVG, but not
    plain local paths.
  - The security reviewer independently reproduced the Ghostscript case.
- **Impact:**
  - A crafted file from a download or archive exposes Ghostscript, PDF and SVG parsers.
    These have had code-execution CVEs.
  - It can also copy other local images into a file the user later shares.
  - The extension allow-list gave no protection.
- **Fix:**
  - `sniff_coder()` detects JPEG, PNG, GIF, WebP, TIFF, BMP, JPEG XL, AVIF and HEIC from
    the file signature.
  - Every input is passed as `CODER:/absolute/path`. Anything else is refused with
    "Not a supported image".
  - Correctly encoded files with a wrong extension still work.
- **Verification:**
  - `test_disguised_non_raster_input_is_refused` covers PS, SVG, MVG and PDF.
  - `test_misnamed_real_image_still_works`.
  - `test_sniff_coder_matches_real_files` covers 8 formats, each on whichever ImageMagick
    can write it.
  - Qt test `test_oversized_and_disguised_files_flagged` and GTK test
    `test_non_utf8_filename_and_disguised_file`.
  - The new tests fail on the v1.1.0 backend and pass on the fix.
  - They passed on Ubuntu, Debian, Fedora and Windows CI.

#### SEC-2: No resource limits (decompression bombs). **Medium**. Fixed.

- **Where:** `image_processor.py`. No size checks and no `-limit` options. Up to 4
  parallel jobs, plus thumbnail rendering.
- **Evidence:**
  - A 388,871-byte PNG of 20000×20000 px took 3.2 GB of RAM to convert.
  - The reviewer saw 1.95 GB for a 17 KB file.
  - ImageMagick's default limits (area 200 GP, disk unlimited) don't stop this.
- **Impact:** the machine freezes, swaps or fills its disk. Local denial of service only.
- **Fix:**
  - Images over `MAX_PIXELS` (200 MP) are refused after a cheap `-ping` and before any
    decoding: in `process_image`, in `thumbnail`, and when images are added to either
    interface.
  - The Windows bundle also gets policy resource limits (SEC-3).
- **Verification:**
  - `test_huge_dimensions_refused_before_decoding` uses a 900 MP header in 100 bytes and is
    refused in well under 10 s.
  - The Qt GUI test flags `bomb.png` as "too large".

#### SEC-3: The bundled Windows ImageMagick used the portable build's open policy. **Medium**. Fixed (defence in depth).

- **Where:** `windows/build.ps1`, which copied `*.xml` from the portable archive.
- **Evidence:**
  - Upstream's open policy restricts nothing.
  - `MSVG:` was readable on Windows before this change. It is SEC-1's SVG renderer, and
    the portable build has no librsvg.
- **Fix:** `windows/imagemagick-policy.xml` is installed as `policy.xml`. It sets:
  - no delegates;
  - PS, PDF, XPS, SVG, MSVG, MVG, MSL, TEXT, URL and similar coders denied;
  - no `@file` lists;
  - memory, map, disk, width and height limits.
- **Verification:** Windows CI `bundle-check` asserts:
  - the policy is active;
  - MSVG, SVG, MVG, PS, PDF and TEXT are refused with "not authorized";
  - AVIF still round-trips under the policy.

  Passed in run 41375669686. Also checked locally with ImageMagick 7.1.2 via
  `MAGICK_CONFIGURE_PATH`.

#### SEC-4: Error messages leaked full paths with ImageMagick 7. **Low**. Fixed.

- **Where:** `_clean_error`. The regex only handled IM6's `` `path' `` quoting.
- **Evidence:**
  - IM7 prints `'path'`, so paths were never removed on Fedora or Windows.
  - Paths containing an apostrophe were also mangled.
- **Fix:** handle both quote styles, an optional coder prefix, and apostrophes in paths.
- **Verification:** `test_real_errors_hide_paths` runs real ImageMagick output in a folder
  named `it's private`.

#### SEC-6: Animated and multi-page files bypassed the pixel limit. **Medium**. Fixed (found during v1.1.1 validation).

- **Where:** `image_processor.py`. `identify` checked only the first frame against
  `MAX_PIXELS`, but the conversion read every frame and then deleted all but the first
  (`-delete 1--1`).
- **Evidence:** an 88 KB GIF with eight 4000 × 4000 frames used 2.0 GB of RAM in
  ImageMagick 7.1.2-34 on Fedora 44; 16 frames (under 1 MB) used 3.9 GB. Linux has no
  ImageMagick memory or list-length limit by default. On Windows the bundled policy
  (SEC-3) already capped this.
- **Fix:** inputs are read as `CODER:/path[0]`, so only the first frame is decoded.
  Peak memory for the 16-frame file is now about 350 MB.
- **Verification:** `test_animated_frames_cannot_bypass_pixel_limit` builds the 16-frame
  GIF and measures the child processes' peak memory (Linux). It fails on the previous
  code ("ImageMagick used 3918 MB") and passes with the fix. On Windows it checks that
  processing succeeds. Filenames with literal brackets (`x[10x10].png`,
  `frame[0-3].png`), `*`, `@`, `~`, `:` and a leading `-` still convert correctly
  with the `[0]` suffix.
- **Regression found by the independent review (SEC-7):** with `[0]`, ImageMagick expands
  `%d`-style patterns in the input name. My first local check of `100%d.png` passed only
  by coincidence, because a `1000.png` of the same size happened to exist.

#### SEC-7: `%` in a filename could select a different file (regression from the SEC-6 fix). **Medium**. Fixed before release.

- **Evidence (reviewer, reproduced by me):**
  - `p%d.png` (40 × 30) next to `p0.png` (400 × 400): the size check and the conversion
    read `p0.png`, and the output called `p%d.png` contained the other image.
  - `x%03d.png` and `z%%.png` failed with "No such file".
- Never released: it existed only on the audit branch. It could not reach a dangerous
  decoder, because the decoder is still forced.
- **Fix:** with ImageMagick 7, `%` is escaped as `%%`. Ubuntu 24.04 CI showed that
  ImageMagick 6.9.12 also expands `%d` with `[0]` (the decoy was read), but does not
  accept `%%`. So on IM6, a name containing `%` is read without `[0]`. `identify()` then
  refuses files whose frames total more than `MAX_PIXELS`, and the conversion drops the
  extra frames as in v1.1.0.
- **Verification:** `test_percent_in_filename_reads_that_file` (`p%d`, `x%03d`, `z%%`,
  `50%`, each next to a decoy file). Three of the four cases fail without the fix.
  `test_percent_name_with_many_frames_stays_bounded` covers the IM6 path (refused) and
  the IM7 path (first frame only).

#### SEC-8: Error messages leaked the path when a folder name contained " @ ". **Low**. Fixed.

- **Evidence (reviewer, reproduced by me):** a damaged BMP in `home @ secret/` gave
  "improper image header \`/tmp/…/home". The location suffix was cut at the first " @ ",
  inside the path, before the path was removed.
- **Fix:** the quoted path is removed first, then the suffix is cut at the last " @ ".
  This also covers paths that contain an apostrophe followed by a space.
- **Verification:** `test_error_hides_path_with_at_sign`. It fails before the fix.

#### SEC-9: Defence-in-depth gaps from the independent review. **Low**. Fixed.

- **Policy deny list:** the reviewer found TMP, MPC, CACHE, FD, MPR, WMF, EMF, CLIPBOARD
  and SCREENSHOT were not denied. They are added now. I confirmed locally that MPC and
  MPR are refused. TMP and FD showed no observable effect either way (the test file was
  not deleted). These coders are unreachable anyway, because every input gets an
  explicit raster decoder. INFO was not denied: the tests use `info:` output.
- **Panoramas:** the policy's 64K-pixel width and height limit refused a 70000 × 100
  panorama that passes the 200-megapixel check, which Linux accepts. Raised to 256K.
  The memory, map and disk limits still apply.
- **Qt previews:** `QImageReader` could fall back to detecting the format from content,
  and the SVG plugin is bundled. The reader now uses the format from `sniff_coder` and
  has content detection off. Other formats (AVIF, HEIC, JXL) use the ImageMagick
  thumbnail as before.
- **upgrade-test:** the download now has a timeout.
- **Accepted:**
  - The time between the size check and the conversion could let a swapped file
    through. That needs an attacker who controls the file during processing.
  - A silent upgrade (for example via winget) aborts while the app is running, because
    of `AppMutex`. This is intended.

#### SEC-5: Symlinked files and a symlinked `output` folder are followed. **Low**. Accepted.

This only matters in folders that other users can write to, which is unusual for
personal photo folders. Output names are reserved with `O_EXCL`, which does not
follow symlinks, so existing files are never overwritten.

#### SUP-1: GitHub Actions were pinned to tags. **Low**. Fixed.

All actions are now pinned to full commit SHAs, with the version in a comment.
Workflows already had `permissions: contents: read` and used no secrets.

#### SUP-2: The installer build is not reproducible; pip installs are not hash-locked. **Low**. Partly fixed.

- The tag-triggered rebuild produced a different installer hash from the released file.
- `windows/requirements.txt` pins the top-level packages with `==` but has no hashes, so
  indirect dependencies can change between builds.
- 7-Zip and Inno Setup come from the runner image.
- Mitigation in place: the release attaches the exact file that CI tested, and publishes
  its SHA-256.
- **Recommendation:** add a hash-locked requirements file
  (`pip-compile --generate-hashes`), and record the runner tool versions.
- **v1.1.1:** `windows/requirements.txt` now pins all 14 packages, including indirect
  ones, with SHA-256 hashes (resolved for Python 3.13 on win_amd64). CI installs them
  with `--require-hashes --only-binary=:all:`. All 14 versions had no OSV advisories on
  2026-11-02. That only means none were known to OSV, not that they are free of
  vulnerabilities. The build is still not byte-for-byte reproducible (PyInstaller and
  Inno Setup embed timestamps; 7-Zip, Inno Setup and Python come from the runner
  image). The release attaches the installer built and tested by the tag's own CI run.

#### SUP-3: Licensing notices may not cover every library statically linked into `magick.exe`. **Low**. Fixed (notices); legal review not performed.

- Covered: Qt/PySide6 (LGPL-3.0, shipped as separate DLLs with license texts), Python
  (PSF), and ImageMagick's `LICENSE.txt` and `NOTICE.txt`.
- Not verified: whether the portable `NOTICE.txt` lists every bundled library, such as
  libheif and libde265 (LGPL), aom, dav1d, libjxl and libwebp.
- LGPL libraries linked statically may require relinking materials.
- **Recommendation:** inspect `NOTICE.txt` from the archive and extend
  `THIRD-PARTY-NOTICES.txt`, or confirm upstream's compliance position.
- The wrong license paths in `THIRD-PARTY-NOTICES.txt` were fixed (WIN-8).
- **v1.1.1 findings:**
  - The `NOTICE.txt` in the pinned portable archive (SHA-256 `34db4364…bbf1`) lists 41
    libraries with their license texts and exact source revisions. The archive has no
    Ghostscript. `gslib` in `magick -version` only means ImageMagick can use an
    installed Ghostscript, and the policy blocks it anyway.
  - The LGPL libraries linked statically into `magick.exe` are cairo, libcroco,
    fribidi, gdk-pixbuf, glib, liblqr, pango, libraw, librsvg, libde265 and libheif.
    `THIRD-PARTY-NOTICES.txt` now names them and points to ImageMagick's published
    corresponding source and Windows build scripts. Magick Studio redistributes the
    unmodified official binary.
  - Missing from the notices before: **OpenSSL 3** (`libcrypto-3*.dll`, `libssl-3*.dll`,
    Apache-2.0, from Python and Qt), **Mesa llvmpipe** (`opengl32sw.dll`, MIT), Qt's
    internal third-party code, Python's xz/expat/mpdecimal, and the MSVC runtime. All are
    now listed. The Apache-2.0 text is shipped in `_internal\licenses\`, and
    `bundle-check` requires it.
  - **Remaining:** this is an engineering review, not legal advice. Patent questions
    (HEVC via libde265, H.264 via openh264) are not assessed.

### Backend and concurrency

#### BE-1: Linux: *Quit* (Ctrl+Q) during processing hid the window but kept processing. **Medium**. Fixed.

- **Where:** `main.py`. The `quit` action called `Application.quit()`, which does not emit
  `close-request`, so the batch was never cancelled.
- **Evidence:**
  - Reproduced with 16 large images. The window closed, but the process kept running for
    about 30 s and wrote all 16 outputs.
  - After the fix it exits in 8 s, with 0 outputs and no temp files.
  - Also present in v1.0.0.
- **Severity:** the reviewer proposed High. It is rated Medium because no data is lost and
  only the requested outputs are written, but the app keeps working invisibly.
- **Fix:** `on_quit()` runs the same cancel/shutdown handler as closing the window, then
  quits.
- **Verification:** `test_quit_cancels_running_batch` triggers the real `quit` action. It
  fails on v1.1.0 and passes on the fix.

#### BE-2: Linux: a non-UTF-8 file name stopped a folder import at "Scanning…". **Medium**. Fixed.

- **Where:** `main.py`. `GLib.markup_escape_text(path.name)` raised `UnicodeEncodeError`
  inside the idle callback.
- **Evidence:** reproduced with `caf\xe9.jpg`. The rest of the folder was never listed.
- **Fix:** a `display()` helper makes names and paths safe for GTK.
- **Verification:** `test_non_utf8_filename_and_disguised_file` fails on v1.1.0 and passes
  on the fix.

#### BE-3: The preview waited behind all thumbnails. **Medium** (responsiveness). Fixed.

- **Evidence:** importing 120 JPEGs of 3000×2000 showed the first preview after 12.41 s.
  After the fix it appears after 0.21 s (Qt, offscreen).
- **Fix:** both interfaces use a separate single-worker preview executor.

#### BE-4: Qt decoded thumbnails at full resolution. **Low**. Fixed.

- **Evidence:** a 63 MP JPEG took 0.87 s and 295 MB, against 0.14 s and 58 MB when scaled.
- **Result:** for the 120-image import, all thumbnails now load in 1.84 s instead of 12.35 s.
- **Fix:** `QImageReader.setScaledSize` before `read()`.

#### BE-5: Linux: Ctrl+Enter could start a partial batch while images were still loading. **Low**. Fixed.

`start_processing` now checks whether the button is sensitive, matching Qt. Verified
with the reviewer's reproduction script.

#### BE-6: Unexpected exceptions could leave items at "Reading…" or the UI stuck in "busy"; Qt raised `RuntimeError` when closed mid-batch. **Low**. Fixed.

- **Fix:**
  - The loaders catch all exceptions and always report back.
  - The batch threads always emit or schedule `batch_done` (`try/finally`).
  - Qt ignores signals whose source was deleted.
- **Evidence:** the close-mid-batch reproduction no longer prints a traceback. No temp
  files or orphaned processes were left, either before or after the fix.

#### BE-7: `MAGICK_STUDIO_MAGICK` was barely validated. **Low**. Fixed.

- **Before:** any existing file was accepted, including non-executables, and bare names
  were rejected.
- **Now:** the value is resolved with `shutil.which`.
- **Verification:** `test_detect_env_override` covers a full path, a bare name on PATH, a
  missing file and a non-executable file.

#### BE-8: `thumbnail()` has no timeout or cancellation. **Low**. Open.

A pathological file could occupy a loader thread until ImageMagick finishes. SEC-2/3
greatly reduce the cases.

**Recommendation:** pass a timeout through `_run`.

#### BE-9: Minor efficiency issues. **Low**. Open.

- The WebP-quality probe runs on the GUI thread once.
- Linux progress counting is O(n) per item.

Neither was noticeable below thousands of images.

#### Not reproduced

- **Closing the Qt window mid-batch leaves temp files or orphaned `magick` processes.**
  Tested on Linux by me and by the reviewer: none were left.
- **Output-name race between parallel workers.** Six sources converting to the same name,
  5 runs, gave 6 distinct files every time with no overwrites.

### Windows interface and installer

#### WIN-1: "Upgrade" was only tested as re-installing the same version. **Medium**. Fixed (v1.1.1).

- 1.1.0 is the first Windows release, so a real upgrade could not be tested.
- The README now says this.
- **Recommendation:** for v1.1.1, install the v1.1.0 installer in CI and upgrade it with
  the new one.
- **v1.1.1:** `winci.py upgrade-test` (CI step "Upgrade from the published previous
  release") does this:
  1. downloads the published v1.1.0 installer;
  2. checks its SHA-256 against a pinned value and the release's `SHA256SUMS.txt`;
  3. installs it, then converts images and opens the window with it;
  4. installs the candidate over it;
  5. checks that the only uninstall entry and the file version are now 1.1.1;
  6. opens the upgraded app and converts JPEG, PNG, WebP and AVIF with it;
  7. checks the originals by SHA-256, and that there is exactly one Start Menu
     shortcut, one uninstall entry and one uninstaller;
  8. uninstalls, and checks that the folder, shortcut and entry are gone and the user
     images and outputs remain.

  Passed first in run 41378401714. This ran on a Windows Server 2025 runner, not a
  desktop PC.

#### WIN-2: Uninstalling while the app was running was not prevented. **Medium**. Fixed.

- **Fix:** the app creates the `MagickStudio.Running` mutex, and the installer declares
  `AppMutex`. Setup and uninstall now ask the user to close the app first.
- **Verification:** the Windows CI `install-test` starts the installed app, runs the silent
  uninstaller and asserts that it refuses (exit code 1) and leaves the files. It then
  uninstalls normally and checks the exit code. Passed in run 41375669686.

#### WIN-3: Windows 10, high DPI and dark mode were not really verified. **Medium**. Partly fixed.

- **Fixed:** the dark-mode screenshot is now checked. Window lightness was 43 dark versus
  227 light in run 41375669686.
- **Open:**
  - CI runs only on Windows Server 2025 (Windows 11 24H2 codebase) at 100 % scaling with
    the `windows11` style.
  - Windows 10, other scaling factors and real desktops remain **untested**, as the
    README states.

#### WIN-4: Minimum Windows version too low. **Low**. Fixed.

`MinVersion=10.0.17763` matches Qt 6's documented minimum of Windows 10 1809.

#### WIN-5: Setup could delete an unrelated `_internal` folder. **Low**. Fixed.

- **Risk:** if a user typed an existing folder of another PyInstaller app as the install
  directory, that app's `_internal` would be wiped.
- **Fix:** `[InstallDelete]` now runs only when the folder already contains
  `MagickStudio.exe`.

#### WIN-6: Windows on ARM wording. **Low**. Fixed.

The installer allows only x64 Windows (`x64os`), so on ARM64 it refuses to run. The
README wrongly said that "the app doesn't start".

#### WIN-7: PyInstaller would use UPX if a developer had it on PATH. **Low**. Fixed.

Fixed with `--noupx`.

#### WIN-8: `THIRD-PARTY-NOTICES.txt` pointed to `licenses\` instead of `_internal\licenses\`. **Low**. Fixed.

#### WIN-9: Untested on Windows: locked output folders (ACLs) and paths over 260 characters. **Low**. Open.

`test_unwritable_output_dir` is POSIX-only.

**Recommendation:** add an `icacls` test and a long-path test.

### Linux regressions and CI

No Linux regression from the Windows work was found. The reviewer compared v1.0.0 and v1.1.0:

- `install.sh`, `uninstall.sh` and the Linux workflow were unchanged.
- No new dependencies.
- Hidden-folder logic, output permissions and the IM6 fallback were identical.

#### CI-1: Silent skips could leave Linux CI green with no GUI or `cwebp` coverage. **Medium**. Fixed.

- **Fix:** with `MAGICK_STUDIO_REQUIRE_ALL=1` (set in Linux CI), a missing display or
  missing `cwebp` fails instead of skipping.
- **Effect:** this immediately found a `cwebp` test that needed updating after SEC-1. That
  test is always skipped on developer machines without `cwebp`.

#### CI-2: Gaps in Linux CI coverage. **Medium**. Partly fixed.

- Container jobs run as root, so `test_unwritable_output_dir` is skipped on Debian and
  Fedora. It runs on Ubuntu.
- `install.sh` runs only on Ubuntu.
- The installed launcher is never executed.
- There is no upgrade test from v1.0.0.

**Recommendation:** run the containers with a normal user, and run `install.sh --yes`
on Fedora and Debian.

**v1.1.1:** the Ubuntu job now installs v1.1.0 with its own `install.sh` and upgrades it
with the new one, checking that the installed files match. The other gaps remain.

#### CI-3: Windows CI ignored the uninstaller exit code. **Low**. Fixed.

#### CI-4: Timing-based cancel tests. **Low**. Open.

- Some tests cancel after a fixed delay (0.3 s or 0.4 s).
- None failed in this audit's runs.
- **Recommendation:** cancel once a child process has started.

### Test-quality notes

- **Mock-heavy tests:**
  - `test_console_windows_suppressed` only checks the flags on Linux. The real
    console-window check is the Windows CI `console-check`, which has a negative control.
  - `test_windows_never_uses_system_convert` patches `sys.platform`. Both tests are kept,
    with these limits noted.
- **Still missing:**
  - a test of the Windows installer upgrading from an older version (WIN-1);
  - Linux install tests outside Ubuntu (CI-2).
- **No padding:** the new tests each target one confirmed defect. Each was checked to fail
  on v1.1.0 (where that is meaningful) and to pass with the fix.

## Recommendation

- **Keep v1.1.0.** No Critical issues, no data loss, and the published installer is the
  one that was tested.
- **Prepare v1.1.1** from this branch. It contains the fix for the High finding SEC-1, the
  Medium fixes and the CI hardening.
- **Before tagging v1.1.1:**
  1. bump `APP_VERSION`;
  2. add a CI upgrade test from the v1.1.0 installer (WIN-1);
  3. review the licensing notices (SUP-3).
- **Until then:** users should avoid processing images from untrusted sources.
